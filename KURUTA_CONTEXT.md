# KURUTA — Конституция проекта

> Этот файл — единственный источник истины. Все решения, архитектура, код и поведение системы должны строго соответствовать ему. Любое отклонение запрещено. Любое "улучшение по своему усмотрению" запрещено. Если требование не описано здесь — его нет.

## 1. СУТЬ ПРОЕКТА

KURUTA — двусторонний маркетплейс рекламных размещений с двумя направлениями:

**Направление A — Задания:** Креатор → кампания → много заданий → Амбассадоры выполняют → KURUTA проверяет → вознаграждение.
**Направление B — Рекламные места:** Владелец площадки → выставляет место → Креатор бронирует и оплачивает → Владелец выполняет → KURUTA проверяет → выплата.

KURUTA зарабатывает комиссией 10% (стартовая модель) на направлении B. На направлении A комиссия закладывается в стоимость задания.

**Три роли (совмещаемые):**
- Креатор — покупает размещения
- Амбассадор — выполняет задания за вознаграждение
- Владелец площадки — продаёт рекламные места

Один пользователь может совмещать роли. Переход в "Владелец площадки" требует расширенной ручной проверки.

**ЧТО KURUTA ПРОДАЁТ:** контролируемый результат — выполненные размещения, организованные сделки, проверку, безопасность, репутацию.
**ЧТО KURUTA НЕ ПРОДАЁТ:** просмотры, подписчиков, вирусность, попадания в рекомендации, гарантированный рост.

## 2. СТЕК ТЕХНОЛОГИЙ (ФИКСИРОВАН)

- **Backend:** Node.js 20 LTS + TypeScript 5.x + NestJS (модульная архитектура)
- **Frontend:** Next.js 14+ (App Router) + TypeScript
- **База данных:** PostgreSQL 16 (единственная БД, JSONB только там, где оправдано)
- **ORM:** Prisma (миграции через `prisma migrate`)
- **Кэш / очереди / сессии:** Redis 7
- **Очереди задач:** BullMQ
- **Хранилище файлов:** S3-совместимое (локально MinIO, в проде — совместимый провайдер)
- **Валидация:** Zod (input), class-validator (DTO)
- **Auth:** JWT (access 15 мин) + refresh tokens (ротация) + опциональный TOTP 2FA
- **Payments:** адаптер-интерфейс (реализация через ЮKassa/Stripe — абстрагировано)
- **Логирование:** Winston + структурированные JSON-логи
- **Мониторинг ошибок:** Sentry (интерфейс)
- **Тесты:** Jest + Supertest (e2e), unit-тесты на критичные сервисы
- **CI/CD:** GitHub Actions
- **Контейнеризация:** Docker + Docker Compose (dev и prod профили)
- **Reverse proxy:** Caddy или Nginx (TLS termination)
- **Секреты:** только через `.env`, никогда в коде, никогда в логах

**ЗАПРЕЩЕНО добавлять:** другие языки, другие БД (MySQL/MongoDB), другие ORM (TypeORM/Sequelize), другие фронтенд-фреймворки, любые "альтернативы потому что модные".

## 3. ПРИНЦИПЫ БЕЗОПАСНОСТИ (НЕПРИКОСНОВЕННЫ)

### 3.1. Defense in depth
Каждый слой имеет свою защиту. Нельзя полагаться на один барьер.

### 3.2. Zero trust
Внутренние сервисы не доверяют друг другу по умолчанию. Auth проверяется на каждом защищённом эндпоинте. RBAC — на каждой операции.

### 3.3. Least privilege
Каждый пользователь/сервис получает минимум прав, необходимых для операции.

### 3.4. Конкретные требования:
- **Пароли:** Argon2id (не bcrypt, не sha). Соль уникальная на запись.
- **JWT:** RS256 или HS256 с длинным секретом. Access token — короткоживущий (15 мин). Refresh — ротация при каждом использовании. Хранение refresh — httpOnly Secure SameSite=Strict cookie.
- **2FA:** TOTP для финансовых операций (вывод, смена реквизитов) — обязательно.
- **Rate limiting:** на auth (5 попыток/мин), на API (100 req/мин на пользователя), на sensitive-операции (отдельные лимиты).
- **Helmet + CSP:** строгая Content Security Policy, без unsafe-inline где возможно.
- **CORS:** whitelist доменов, не `*`.
- **SQL-инъекции:** только через Prisma parameterized queries. Raw SQL — запрещён, кроме явно ревьюированных случаев.
- **XSS:** React по умолчанию экранирует. Дополнительно — DOMPurify для user-generated HTML (если появится).
- **CSRF:** SameSite cookies + CSRF-token для state-changing операций.
- **SSRF:** запрет исходящих запросов к внутренним IP (127.0.0.0/8, 10.0.0.0/8, 169.254.0.0/16, etc.).
- **Валидация:** ВХОДНЫЕ ДАННЫЕ ВАЛИДИРУЮТСЯ ВСЕГДА. На каждом эндпоинте. Zod-схема обязательна.
- **Файлы:** проверка MIME по содержимому (не по расширению), размер-лимит, антивирусная проверка (ClamAV-интерфейс), хранение вне webroot.
- **Секреты:** `.env` в `.gitignore`. Пример — `.env.example` без значений. Pre-commit hook (husky + gitleaks) блокирует коммиты с секретами.
- **Логи:** НИКОГДА не логировать пароли, токены, реквизиты карт, полные номера телефонов/карт. Маскирование обязательно.
- **Transport:** TLS 1.3 только. HSTS.
- **Зависимости:** Dependabot + audit в CI. Критические уязвимости блокируют merge.

### 3.5. Финансовая безопасность
- Все денежные операции — через **FinancialJournal** (раздел 5).
- Баланс — вычисляемое поле из журнала, не хранится как "число, которое можно поменять".
- Все списания/начисления — в ACID-транзакциях PostgreSQL.
- Двойная запись (double-entry): каждая операция имеет debit и credit.
- Блокировки: `SELECT ... FOR UPDATE` при работе с балансом.
- Идемпотентность: каждая финансовая операция имеет уникальный idempotency-key. Повторный запрос — тот же результат.
- Аудит-лог: каждое изменение денег — запись в audit_log с userId, action, before, after, timestamp, ip, userAgent.
- Минимальный вывод для Амбассадора: 500 ₽ (конфигурируемо).
- Смена реквизитов вывода — временная блокировка вывода + повторная проверка.

### 3.6. Антифрод-сигналы (фиксируются, но не блокируют автоматически — отправляют на ручную проверку):
- Несколько аккаунтов с одинаковыми device fingerprint
- Одинаковые реквизиты вывода у разных пользователей
- Подозрительно быстрое выполнение заданий
- Повторяющиеся скриншоты-подтверждения (перцептивный хэш)
- Резкий рост аудитории без истории
- Нестандартная активность (ночью, с разных GEO за короткое время)

## 4. РОЛЕВАЯ МОДЕЛЬ (RBAC)

Роли и их права:
- `guest` — регистрация, публичные страницы
- `creator` — создание кампаний, покупка мест, просмотр отчётов
- `ambassador` — просмотр/выполнение заданий, вывод средств
- `platform_owner` — создание/продажа рекламных мест, вывод средств
- `moderator` — ручная проверка заявок, заданий, сделок, споров
- `finance` — обработка выплат, возвратов
- `admin` — управление пользователями, конфигурацией
- `superadmin` — управление ролями, системные настройки

**Принцип:** роли назначаются явно, не наследуются по умолчанию. Проверка прав — middleware на каждом защищённом эндпоинте.

## 5. ФИНАНСОВЫЙ ЖУРНАЛ (ОБЯЗАТЕЛЕН)

Сущность `FinancialTransaction`:
```
id (uuid)
idempotencyKey (unique)
type (enum: deposit, reserve, release, reward, fee, payout, refund, adjustment)
userId (связь)
amount (numeric(14,2)) — всегда положительное
currency (пока RUB)
status (pending, completed, failed, refunded)
relatedEntityType (campaign, task, ad_slot, deal, dispute, payout)
relatedEntityId
description
createdAt
metadata (jsonb)
```

**ПРАВИЛА:**
1. Баланс = SUM(type IN deposit, reward, refund) - SUM(type IN reserve, payout, fee) по пользователю.
2. Запрещено обновлять поле `balance` напрямую. Только через создание транзакции.
3. Каждая транзакция атомарна. Ошибка → откат всей транзакции.
4. Транзакции неизменяемы (immutable). Ошибка исправляется только контр-транзакцией.
5. Ежедневная сверка (reconciliation) — отдельный cron.

## 6. СОСТОЯНИЯ ОБЪЕКТОВ (ФИКСИРОВАННЫЕ FSM)

Каждый объект имеет конечный автомат переходов. Переходы — только через явно разрешённые.

**Пользователь:** active → limited → blocked → deleted
**Заявка Амбассадора:** draft → pending → needs_info → approved | rejected | suspended
**Кампания:** draft → awaiting_payment → pending_review → approved → active → paused → completed | cancelled
**Задание:** available → taken → in_progress → proof_submitted → reviewing → approved → paid | rejected | resubmit_required | overdue | cancelled | disputed
**Рекламное место:** draft → pending_review → published → booked → in_progress → confirming → completed | closed
**Сделка (бронь):** created → paid → in_progress → confirming → completed | disputed | cancelled
**Выплата:** requested → checking → processing → paid | error | cancelled
**Спор:** opened → investigating → resolved_creator | resolved_executor | resolved_partial | closed

Переходы валидируются на уровне сервиса. Недопустимый переход → ошибка.

## 7. МОДЕРАЦИЯ (РУЧНАЯ, ОБЯЗАТЕЛЬНАЯ)

Ручная проверка требуется для:
- Заявки на роль Амбассадора
- Заявки на роль Владельца площадки
- Кампании (перед активацией)
- Подтверждения выполнения задания
- Подтверждения выполнения рекламного заказа
- Спора
- Повторной верификации Амбассадора (периодически)
- Смены реквизитов вывода (при подозрении)

Интерфейс модератора — отдельное приложение/роль с полным аудит-логом действий.

## 8. УВЕДОМЛЕНИЯ

Каналы: in-app (обязательно), email (обязательно), push (опционально в v1).
События — согласно разделам 55–57 оригинального ТЗ.
Очереди через BullMQ. Ретраи с exponential backoff. Dead letter queue.

## 9. АУДИТ-ЛОГ

Таблица `audit_log`:
```
id, userId, action, entityType, entityId, before (jsonb), after (jsonb), ip, userAgent, timestamp
```
Записываются ВСЕ значимые действия: auth, создание/изменение/удаление сущностей, финансовые операции, действия модераторов, смена ролей.
Логи неизменяемы (append-only). Хранение — минимум 3 года.

## 10. АРХИТЕКТУРНЫЕ ОГРАНИЧЕНИЯ

- **Монорепо** (Turborepo или Nx): `apps/api`, `apps/web`, `apps/admin`, `packages/shared`, `packages/database`
- **Модульность в API:** каждый домен — отдельный NestJS-модуль (users, auth, campaigns, tasks, ad_slots, deals, finance, disputes, notifications, audit, moderation)
- **Слои:** Controller → Service → Repository (Prisma). Бизнес-логика — только в Service.
- **DTO:** отдельные классы для input/output. Никогда не возвращать entity напрямую.
- **Error handling:** глобальный exception filter. Единый формат ошибок.
- **Конфигурация:** через `@nestjs/config`, валидация через Joi/Zod при старте.
- **Тесты:** покрытие критичных сервисов (finance, auth, moderation) — минимум 80%.
- **Миграции:** только через `prisma migrate`. Ручные SQL-миграции запрещены.
- **Коммиты:** Conventional Commits (`feat:`, `fix:`, `refactor:`, `chore:`, `docs:`).
